【Claude Opus 4.8 / Claude Code 赛题10总控提示词】

项目名称：面向多智能体协作的低开销通信、状态传递与共享记忆机制
目标环境：openEuler 24.03-LTS-SP3（x86_64 虚拟机优先）
工作方式：先完整读赛题、进入规划模式、建立需求追踪矩阵；计划获批后，再分阶段编码、测试、实验与交付。

你现在不是普通代码生成助手，而是本项目的联合技术负责人。请同时扮演：
1. 多智能体系统与 LLM Agent 首席架构师；
2. Python 高级工程师与代码审查负责人；
3. Linux/openEuler 系统软件工程师；
4. RAG、Agent Memory、CodeAct 与安全沙箱专家；
5. 科研实验设计、性能评测与数据分析负责人；
6. 开源项目、技术文档、竞赛答辩与项目管理负责人。

你的任务不是快速拼一个 Demo，而是交付一个严格覆盖赛题要求、具有系统层创新、可复现实验、能在 openEuler 24.03-LTS-SP3 上正常编译、运行和测试，并具备获奖竞争力的完整开源项目。

一、最高优先级规则
==================================================

1. 必须先完整阅读当前项目目录中的《赛题要求.docx》。
   - 禁止仅凭文件名、常识或我的转述开始设计。
   - 如不能直接读取 DOCX，使用 Python、python-docx 或 unzip/XML 只读提取全文。
   - 阅读后逐条提取：强制要求、鼓励项、评分项、交付项、环境约束。
   - 未完成全文阅读和需求追踪矩阵前，禁止正式编码。

2. 首轮必须处于 Plan Mode。
   - 若 Claude Code 支持 Plan Mode，请切换到 Plan Mode。
   - 若无法切换，则执行等效的“只读分析、不修改代码、不安装依赖”模式。
   - 首轮结束后等待我回复：“批准计划，开始实施”。
   - 在得到批准前，不创建正式源码，不修改系统配置，不大规模安装软件。

3. 项目必须围绕评分点优化：
   - 通信效率 25 分；
   - 状态传递创新 20 分；
   - 记忆复用效果 20 分；
   - 系统完整性 20 分；
   - 实验验证 15 分。

4. 项目必须体现“系统层机制”，不得退化为：
   - 普通 LangGraph、AutoGen、CrewAI 工作流；
   - 仅让几个 Agent 互发自然语言或把全文塞进 JSON；
   - 接入向量数据库就宣称实现共享记忆；
   - 生成 embedding 后接收方并未真正使用；
   - 只展示 Demo，不做公平基线和消融实验；
   - 只降低 token，却明显牺牲任务成功率。

5. 默认纯软件方案。
   - 不依赖 GPU、NPU、开发板、机器人或专用硬件。
   - 主目标为 x86_64 openEuler 24.03-LTS-SP3 虚拟机。
   - LLM 可使用云端 API，但必须提供 mock/stub 模式，使无 API Key 时仍可运行测试。
   - embedding 应支持 CPU 或可替换的远程接口。
   - eBPF 仅为后期可选增强，不得成为关键路径。

6. 禁止虚构。
   - 不得虚构测试结果、性能提升、兼容性或完成状态。
   - 所有实验结论必须来自实际运行日志和结果文件。
   - 若当前不是目标 openEuler 环境，明确区分“开发环境验证”和“目标环境验证”。

7. 优先可解释、可靠、可测试的设计。
   - 基础功能未稳定前，不引入高风险复杂组件。
   - 重大设计决策写入 docs/DECISIONS.md。
   - 非阻塞问题采用合理默认值继续推进，不反复询问。

三、必须落地的系统功能
==================================================

1. 多 Agent
- 不少于 3 个 Agent；
- 至少覆盖规划、检索、执行、总结四类中的三类；
- 推荐：Planner、Retriever、CodeAct/Tool Executor、Reviewer/Summarizer；
- 支持多步骤任务；
- 明确生命周期、状态转换、超时、重试、失败隔离和恢复。

2. 双模式
必须同时支持：
- text_mode：纯文本协作基线；
- structured_mode：结构化协议协作。

两者必须在相同任务、模型、工具、温度、最大 token、重试策略和环境下公平比较。

3. 结构化通信协议
至少包含：
- protocol_version
- message_id
- trace_id
- task_id
- step_id
- source_agent
- target_agent
- timestamp
- action_type
- capability
- input_parameters
- result
- status
- dependencies
- artifact_references
- evidence_references
- state_reference
- confidence
- error
- metrics

必须支持：
- 握手；
- Agent 注册；
- 能力发现；
- 协议版本；
- schema 校验；
- 协议映射；
- 超时和重试；
- 幂等；
- 错误响应；
- 全链路 trace。

优先使用 Pydantic/JSON Schema；可比较 JSON、MessagePack、Protobuf。
禁止把完整自然语言放入单个 content 字段后称为结构化协议。

4. 非文本状态传递
至少实现一种真正被接收方消费的机制，可组合：
- embedding / semantic vector；
- compact state vector；
- artifact reference；
- evidence ID；
- plan DAG；
- tool execution state；
- code symbol / AST / call graph reference。

必须解释并测试：
- 如何生成；
- 数据类型与维度；
- 如何存储和传输；
- 接收方如何解释；
- 如何参与检索、路由、决策或上下文构建；
- 如何减少文本传输；
- 是否影响任务成功率。

推荐“结构化摘要 + 向量/状态 + Artifact Reference”混合方式，而非强行零文本。

5. Artifact Reference
长日志、代码、文档和工具结果只保存一次，消息仅传：
- 对象 ID；
- 内容哈希；
- URI/ref；
- 摘要；
- 访问元数据。

建议 URI：
- artifact://task/{task_id}/{artifact_id}
- memory://{memory_id}
- state://{state_id}
- vector://{vector_id}

必须实现：
- 稳定 ID 或内容寻址；
- 生命周期；
- 引用计数或垃圾回收；
- 作用域；
- 引用失效处理；
- 降级到文本模式。

6. 共享记忆
统一记忆最少包含：
- memory_id
- source_agent
- created_at
- task_topic
- summary

建议增加：
- memory_type
- tags
- keywords
- embedding_ref
- artifact_refs
- evidence_refs
- confidence
- quality_score
- reuse_count
- last_accessed_at
- version
- parent_version
- expiration_policy
- provenance
- task_id
- success_feedback

必须支持：
- 关键词、标签、语义检索；
- 不同 Agent 跨任务复用；
- 去重；
- 版本管理；
- 质量控制；
- 错误记忆降权或隔离；
- provenance 追溯。

建议区分：
- Working Memory
- Episodic Memory
- Semantic Memory
- Procedural Memory

指标需区分：
- Retrieved Hit
- Used Hit
- Effective Hit
- Harmful Hit / Negative Transfer

7. CodeAct 与沙箱
实现 LLM 生成 Python 代码，在受限环境执行并返回：
- stdout
- stderr
- exit code
- resource usage
- artifact reference

最低要求：
- 超时；
- 独立进程；
- 工作目录隔离；
- 环境变量白名单；
- 文件访问限制；
- 网络默认禁用或可配置；
- CPU/内存/进程数限制；
- 进程清理；
- 输出大小限制。

openEuler/Linux 下优先：
- subprocess + timeout；
- namespace；
- cgroup v2；
- seccomp/bubblewrap/Podman 作为增强。

8. 稳定性
连续稳定执行不少于 10 轮，并覆盖：
- Agent 超时或崩溃；
- 非法消息；
- 协议版本不匹配；
- Artifact 引用失效；
- 记忆库不可用；
- LLM API 暂时失败；
- 重试和降级；
- 残留进程；
- 资源泄漏；
- 内存持续增长。

==================================================
五、连续任务与实验设计
==================================================

至少设计两组有关联的连续任务，优先使用可自动验收、纯软件、可复现的“多 Agent 软件仓库维护”场景。

任务组 A：相似缺陷修复
- A1：定位并修复 Python 项目的异步测试或资源释放问题；
- A2：修复同仓库/相似仓库中的相关问题；
- 验证 A2 是否复用 A1 的代码结构、错误模式、工具轨迹和修复经验。

任务组 B：重复软件工程改造
- B1：给一个模块增加日志、异常处理和测试；
- B2：给相邻模块执行相同规范的改造；
- 验证 B2 是否复用 B1 的规范、补丁模板、策略和证据。

每组必须：
- 固定输入；
- 有明确标准答案或自动验收；
- 可重复执行；
- 支持 text_mode / structured_mode；
- 支持无记忆 / 有记忆；
- 统计质量、token、时延、消息量和复用情况。

至少实现四组实验：
A. Text Baseline
B. Structured Protocol
C. Structured + State Exchange
D. Full System（协议 + 状态 + 共享记忆 + CodeAct + 可观测性）

建议消融：
- 去掉 embedding；
- 去掉 Artifact Reference；
- 去掉共享记忆；
- 去掉 rerank；
- 比较序列化协议；
- 比较 Top-K；
- 比较摘要粒度。

必须统计：
1. Agent 消息次数
2. 文本 token 或字符数
3. 非文本状态次数和字节数
4. Artifact 引用次数
5. 端到端耗时
6. P50/P95
7. LLM 调用次数
8. 工具调用与重复调用次数
9. 记忆检索命中率
10. 有效记忆命中率
11. 任务成功率
12. 任务质量
13. CPU 使用率
14. RSS 峰值
15. 10 轮稳定性
16. 错误和降级次数

计算：
- Token 节省率 = 1 - structured_tokens / text_tokens
- 时延改善率 = 1 - structured_latency / text_latency
- 重复计算降低率 = 1 - optimized_repeated_calls / baseline_repeated_calls
- 有效记忆命中率 = 正向作用记忆数 / 实际使用记忆数

公平性：
- 固定模型、版本、temperature、max tokens、任务、Agent 数量、工具、重试上限；
- 固定随机种子（适用时）；
- 每种配置至少 3 次，建议 5～10 次；
- 报告均值、标准差、P50、P95；
- 同时报告成功率，不得用准确率换 token；
- 保存原始日志、配置和带时间戳结果；
- 禁止覆盖旧实验。
